# Kalpa Agent Engine: design (egm-draft, 13 Nov 2026)

Akhil, 13 Nov 2026: "Do both, use free Hugging Face and others … we need sell agents … our bread and butter … use these agents and workflows everywhere in all the worlds … engineer standards, best encryption, best UI … compare with competitors and beat them."

## 1. Problem
- Agents run only when GitHub's cron lands (≈5 h of dropped slots on 13 Nov) or when a session pushes.
- n8n sits on Render free (512 MB): Code nodes fail, it sleeps after 15 min; the Claude n8n connector still points at the dead n8n Cloud trial (404).
- We want to **sell** agents. n8n's licence forbids that: "You may use or modify the software only for your own internal business purposes … distribute … only free of charge for non-commercial purposes" (github.com/n8n-io/n8n LICENSE.md, read 13 Nov). So customer agents cannot run on n8n.

## 2. Goals / non-goals
Goals
1. Agents and workflows run 24×7 on free tiers with no card (CLAUDE.md rule 1, 8).
2. One engine reused by every world (b1–b7) and sellable to customers (MIT/Apache parts only on the customer path).
3. Meets the Kalpa standard (147 checks), every secret encrypted at rest and in transit, 5-language replies for any chatbot.
4. Cheaper and more local than Wati / AiSensy / Interakt (§6).
Non-goals: no paid hosting; no customer ever logs in to n8n; no public URL before Akhil says "go" (rule 9).

## 3. Design: three layers
| Layer | Runs on (free) | Job | Licence |
|---|---|---|---|
| **Clock** | Cloudflare Workers cron (never sleeps) + Workflows (durable steps, `step.sleep` up to 365 days) | wake everything on time, ping the Spaces so they never hit the 48 h sleep, start GitHub jobs | our code; Agents SDK MIT |
| **Internal workflows** | **n8n** on Hugging Face Space `kalpa-n8n` (CPU Basic: 2 vCPU, 16 GB) + Supabase Postgres | Kalpa's own 18 flows: daily brief, Task Runner, lead lists, social drafts | n8n SUL, internal use only |
| **Customer agents (sold)** | **Activepieces Community Edition** on Space `kalpa-flows` + Supabase Postgres, `AP_REDIS_TYPE=MEMORY` (single container) | each customer's agent flows: WhatsApp/Telegram replies, bookings, reminders, review asks, lead follow-up | MIT (we never enable `packages/ee`) |
**Tenant isolation (review blocker 1):** Activepieces CE has one project; multi-project, roles, audit logs and embedding are paid. So customer PII and chats stay in BotBhai's own code (per-tenant rows + Supabase row-level security); Activepieces only runs our templates for integrations (Sheets, Calendar, Telegram, Razorpay links), one Space per pilot customer while there are few.
**Public entry (review blocker 2):** a private Space can't receive webhooks, so a Cloudflare Worker is the only public door: it checks Meta's `X-Hub-Signature-256` (and Telegram's secret token), rate-limits, then forwards to the Space with an HF token kept as a Worker secret. Live only after "go".

Plus what exists: GitHub Actions for heavy batch jobs (allowed; no 24×7 loops, GitHub terms) and BotBhai's own Netlify functions for the WhatsApp brain.

### Security (best encryption we can get for free)
- Credentials inside the apps: n8n `N8N_ENCRYPTION_KEY` (n8n encrypts stored credentials with it), Activepieces `AP_ENCRYPTION_KEY` (32 hex, `openssl rand -hex 16`) + `AP_JWT_SECRET`. Generated by Akhil, stored only as Hugging Face Space **secrets**, never in git (gitleaks + TruffleHog already on every push).
- Database: Supabase (Postgres, encrypted at rest by Supabase) through the IPv4 session pooler, TLS with the CA pinned (`DB_POSTGRESDB_SSL_CA` / `AP_POSTGRES_SSL_CA`, reject unauthorized = **true**; today's Render n8n has it `false`, fixed here). Each app gets its own least-privilege role and schema.
- DPDP: data may leave India (HF Spaces run in the US, `region:us`); what the law needs is notice, purpose, deletion, breach reporting and named sub-processors → BotBhai agreement lists Hugging Face, Supabase, Cloudflare and each model provider.
- Customer PII: only what the flow needs; per-customer data retention job; DPDP processor clause already in BotBhai agreement.
- Customer code steps: `AP_EXECUTION_MODE=SANDBOX_CODE_ONLY` (V8 isolates, weaker than process isolation) **and** no customer-written code steps at all: only our reviewed templates.
- Keys rotated every 90 days; backup job uses a read-only role.
- Containers run as non-root, versions pinned (no `latest`), telemetry off, owner login + MFA on both UIs; Spaces stay **private** until "go".

### Reliability
- Space restarts and the in-memory queue lose delayed jobs → scheduled work (reminders 24 h / 2 h ahead) lives as rows in Postgres and the Cloudflare clock re-fires due rows; a restart-mid-run test is part of A241. Every flow is idempotent (booking lock already in `book_slot`), webhook senders retry, Cloudflare pings `/healthz` every 5 min and alerts on Telegram after 3 failures.
- Supabase free pauses after 7 days idle → the clock writes a heartbeat row daily.
- Backups: nightly `pg_dump` of both schemas to a private GitHub Actions artifact (encrypted with `age`, key held by Akhil).
