# K088 · Plain checklist: what a secret scanner must catch in our repo (A205 prep)

1. API Keys
- Why: Attackers use leaked credentials to run expensive AI or cloud workloads at your expense.
- Example: `AKIAFAKE1234567890AB`

2. Webhook URLs with tokens
- Why: Exposure lets malicious actors spoof events or inject unauthorized payloads into your services.
- Example: `https://hooks.slack.com/services/T00/B00/FAKEtoken123456789`

3. Environment files (.env)
- Why: Bundles multiple production secrets together in one easily readable plaintext file.
- Example: `DATABASE_URL=postgres://user:FAKEpassword@localhost:5432/db`

4. Private cryptographic keys
- Why: Allows anyone to decrypt encrypted data or impersonate your servers via SSH or TLS.
- Example: `-----BEGIN RSA PRIVATE KEY-----\nMIIFAKE...\n-----END RSA PRIVATE KEY-----`

5. Service account JSON files
- Why: Grants full programmatic access to cloud project resources and data storage buckets.
- Example: `{"type": "service_account", "private_key": "-----BEGIN PRIVATE KEY-----\\nFAKE..."}`

6. Bot tokens
- Why: Compromises chat or automation bots, allowing spammers to hijack communication channels.
- Example: `123456789:AAF_FAKE_BOT_TOKEN_ABCDEFGHIJK`

7. Database connection strings
- Why: Direct exposure of database credentials allows attackers to dump, alter, or delete all user records.
- Example: `mongodb+srv://admin:FAKEpass@cluster.mongodb.net/prod`

8. JWT secret keys
- Why: Enables attackers to forge valid authentication tokens and impersonate any user or admin.
- Example: `JWT_SECRET=supersecretFAKEYJWTkey1234567890`

9. OAuth client secrets
- Why: Lets malicious applications request user authorization tokens on behalf of your legitimate app.
- Example: `OAUTH_CLIENT_SECRET=fake_secret_abc123xyz789`

10. Basic auth header strings
- Why: Hardcoded credentials in source code provide immediate access to protected internal endpoints.
- Example: `Authorization: Basic ZmFrZTpwYXNzd29yZA==`
