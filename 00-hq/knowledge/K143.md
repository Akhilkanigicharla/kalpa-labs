1. Logins
* **What 'done' means:** Supabase Auth manages user authentication via magic links or passwordless OTPs, returning JWT access tokens to the frontend without raw credentials stored in custom database tables.
* **File or setting to look at:** `supabase/config.toml` [UNVERIFIED: exact file location] or Supabase Dashboard Auth settings.
* **Concrete test:** `curl -i -X POST "https://<PROJECT_REF>.supabase.co/auth/v1/signup" -H "apikey: <ANON_KEY>" -H "Content-Type: application/json" -d '{"email":"test@example.com","password":"testpassword"}'`
* **Usual mistake:** Writing custom login endpoints or storing plain/hashed passwords directly in `public.users` instead of using `auth.users`.

2. IDOR (Insecure Direct Object Reference)
* **What 'done' means:** Netlify functions and database queries verify that the authenticated `auth.uid()` owns the exact requested record ID before reading or modifying it.
* **File or setting to look at:** `01-botbhai/botbhai/core/functions/chat.js` (or applicable Netlify serverless function file).
* **Concrete test:** `curl -i -X GET "https://<APP_DOMAIN>/.netlify/functions/chat?id=<OTHER_USER_RECORD_ID>" -H "Authorization: Bearer <USER_JWT>"` (must return 403 HTTP status or empty result).
* **Usual mistake:** Querying records using only the URL parameter ID without checking `WHERE user_id = auth.uid()`.

3. Row-level security (RLS)
* **What 'done' means:** Every table in the `public` schema has Row-Level Security explicitly enabled, with restrictive policies for SELECT, INSERT, UPDATE, and DELETE.
* **File or setting to look at:** Supabase SQL Editor or schema migration files.
* **Concrete test:** `SELECT tablename, rowsecurity FROM pg_tables WHERE schemaname = 'public';` (all rows must return `rowsecurity = true`).
* **Usual mistake:** Creating public tables in Supabase without executing `ALTER TABLE <table_name> ENABLE ROW LEVEL SECURITY;`.

4. Backups
* **What 'done' means:** Automated daily database snapshots or schema and data exports are saved to an isolated storage location.
* **File or setting to look at:** Supabase Project Settings > Database [UNVERIFIED: exact UI path] or a scheduled export script in `.github/workflows/` [UNVERIFIED].
* **Concrete test:** `pg_dump -h db.<PROJECT_REF>.supabase.co -U postgres -d postgres --schema-only`
* **Usual mistake:** Assuming the free plan includes automatic local database file downloads without configuring scheduled backup exports.

5. Audit logs
* **What 'done' means:** Critical data changes (such as role changes, deletions, or billing events) write immutable append-only rows to an `audit_logs` table via triggers or functions.
* **File or setting to look at:** SQL migration file defining audit triggers or the `audit_logs` table definition.
* **Concrete test:** `INSERT INTO public.orders (id, amount) VALUES ('test_id', 100); SELECT * FROM public.audit_logs WHERE record_id = 'test_id';`
* **Usual mistake:** Giving public write or delete access on the `audit_logs` table to standard user roles.

6. Token expiry
* **What 'done' means:** JWT access tokens expire within a short window (e.g., 3600 seconds) and client applications automatically refresh them using refresh tokens.
* **File or setting to look at:** Supabase Dashboard > Auth Settings > JWT Expiration [UNVERIFIED: exact UI location].
* **Concrete test:** `curl -i -X POST "https://<PROJECT_REF>.supabase.co/auth/v1/token?grant_type=refresh_token" -H "apikey: <ANON_KEY>" -d '{"refresh_token":"<EXPIRED_REFRESH_TOKEN>"}'`
* **Usual mistake:** Exposing long-lived `service_role` keys inside frontend application code instead of using short-lived user tokens.

7. Secret rotation
* **What 'done' means:** Sensitive keys (API keys, webhook secrets) reside strictly in environment variables and can be rotated in settings without requiring code rewrites.
* **File or setting to look at:** Netlify Site Configuration > Environment variables [UNVERIFIED: site settings link] or `01-botbhai/botbhai/netlify.toml`.
* **Concrete test:** Update a webhook secret key in Netlify environment settings and issue a test payload to verify authorization passes with the new key.
* **Usual mistake:** Hardcoding API keys or webhook secret strings inside source files.

8. Soft deletes
* **What 'done' means:** Table rows are soft-deleted by setting a `deleted_at` timestamp column, and active queries filter out records where `deleted_at IS NOT NULL`.
* **File or setting to look at:** SQL table definitions and RLS policy definitions.
* **Concrete test:** `UPDATE public.jobs SET deleted_at = NOW() WHERE id = 'job_123'; SELECT * FROM public.jobs WHERE id = 'job_123' AND deleted_at IS NULL;` (must return zero rows).
* **Usual mistake:** Running raw `DELETE FROM table_name` queries, resulting in unrecoverable data loss and breaking foreign key references.
